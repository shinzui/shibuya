# Improvement Request: Represent Application-Defined Permanent Processing Failures in Dead-Letter Reasons

## Status

Released in [`v0.9.0.0`](https://github.com/shinzui/shibuya/releases/tag/v0.9.0.0)
through `docs/plans/32-add-application-defined-dead-letter-reasons.md`. The published packages
are [shibuya-core 0.9.0.0](https://hackage.haskell.org/package/shibuya-core-0.9.0.0) and
[shibuya-metrics 0.9.0.0](https://hackage.haskell.org/package/shibuya-metrics-0.9.0.0).
This release satisfies the upstream prerequisite for the declarative router-selection failure
policy requested by `mori://shinzui/keiro/okf/improvement-requests/concepts/IR-9`.

## Context

`Shibuya.Core.Ack` describes acknowledgement decisions as semantic outcomes chosen by handlers,
with the framework owning their mechanics.  `AckDeadLetter` nevertheless accepts a closed
`DeadLetterReason` vocabulary containing only `PoisonPill Text`, `InvalidPayload Text`, and
`MaxRetriesExceeded`.

A handler can permanently reject a syntactically valid message for an application-level reason.
For example, a checked router generated by `mori://shinzui/keiro/packages/keiro-dsl` may be
configured to dead-letter an empty recipient selection, a conflicting pair of commands for one
physical target, or a recipient-cap overflow.  None is a poison message, invalid payload, or
exhausted retry budget.  Encoding it with one of the existing constructors makes DLQ payloads,
traces, logs, and operator explanations inaccurate.

## Requested Change

Add a public, stable way to carry an application-defined permanent processing failure through
`AckDeadLetter`.  Prefer a structured reason with a machine-stable code and human-readable detail,
or another design that remains useful to adapters without requiring Shibuya to know each consumer
domain.  Expose a canonical public code/detail or encoding function so adapters do not duplicate
an exhaustive match over Shibuya's constructor vocabulary.  Do not turn poison, payload validation,
retry exhaustion, and application rejection into aliases.

Update Shibuya's tracing/rendering and batch/property tests for the new reason.  Specify the PVP
and migration impact of extending or replacing the current closed sum.  Document the boundary:
the handler chooses the semantic reason, while an adapter transports it to its DLQ representation
without interpreting consumer-specific codes.

## Acceptance

1. A public-only handler can return `AckDeadLetter` for a valid message with a stable application
   reason code and explanatory detail, without using `PoisonPill`, `InvalidPayload`, or
   `MaxRetriesExceeded`.
2. Supervised and batch processing accept the reason, resolve one decision per delivery, and
   preserve retry-idempotent finalization with the complete reason.
3. Total public projections expose structured code and optional detail for every built-in and
   application reason, while canonical rendering preserves the existing built-in strings exactly.
4. Core tracing exposes the stable reason code as a structured attribute and uses the canonical
   code/detail form in error status without a partial or catch-all pattern.
5. Adapter authors have a documented serialization contract that preserves the application reason;
   adapters do not need to understand the consumer's domain vocabulary or reproduce a closed match
   over core constructors.
6. Documentation tells applications to keep details bounded and free of secrets, payloads, raw SQL,
   and unrestricted backend error text.
7. Existing reason constructors retain their meanings, and the 0.9 release notes state the
   exhaustive-pattern migration, PVP consequence, and version-bound changes.
8. The API ships in a tagged `shibuya-core` release before Keiro claims declarative router
   dead-letter policies are supported.

## Requested Deliverables

- Public application-defined dead-letter reason API in `shibuya-core`.
- Canonical public code/detail or encoding API plus core rendering, batch, property, and
  public-surface tests.
- Adapter-facing serialization documentation and consumer migration notes.
- Tagged release.

The PGMQ adoption is tracked separately by
`mori://shinzui/shibuya-pgmq-adapter/okf/improvement-requests/concepts/IR-1`.
